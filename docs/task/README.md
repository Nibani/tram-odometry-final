# Задача и исходные условия

Проект решает кейс «Резервная одометрия по модели» хакатона Московского транспорта. Нужно оценивать скорость и положение трамвая по скоростям передней и задней тележек и положению контроллера водителя, сохраняя работу при ошибках колёсной одометрии и потере GNSS.

## Источники условий

Ниже изложены условия PDF «Резервная одометрия по модели», README обучающего и проверочного датасетов и последующие ответы организаторов. Оригиналы документов и переписка не публикуются. Существенные требования, геометрия и критерии сохранены здесь и в [уточнениях](ORGANIZER_CLARIFICATIONS_RU.md).

Первоначальное ограничение GNSS только стартовой привязкой изменено последующими ответами: редкие коррекции разрешены. Противоречие про депо отражено явно в таблице.

## Действующие уточнения

| Вопрос | Полученный ответ и применение |
|---|---|
| Проверяемый трамвай | Скриптовая проверка только 30618; учёт других трамваев может быть плюсом технического решения. Идентификатор на входе алгоритму не нужен. |
| Начальный GNSS | Наличие гарантировано. Позднее на вопрос о RTK-fix, обозначенном в вопросе как status=2, также получен ответ «Да». Качество и синхронность пары двух антенн отдельно не гарантированы. |
| Поздний GNSS | Разрешён для коррекции. Организаторы прямо ответили, что оценка за этот вариант не снижается. |
| Старт и финиш | Примерно кольца Щукинской и Таллинской, точные точки не заданы. Ранее подтверждены старт со стоянки и наличие GNSS при возможном старте в середине маршрута. |
| Задний ход | В рамках задачи отсутствует. |
| Координата эталона | XYZ точки base_link, высота учитывается; проверочный bag — пример эталона. EPSG и точный вертикальный датум явно не названы. |
| Маршрут / депо | Поздний конкретный ответ: «Только регулярный маршрут». Ранее был общий ответ о необходимости выдавать позицию независимо от действий трамвая. Это не полная формальная спецификация всех веток. |
| Карта | Основная карта выдана отдельно и, по словам организаторов, в среднем точнее GNSS. Восстановление отсутствующих колец входит в задачу; восстановление и добавление тупиков разрешено. |
| Контроллер | Топик driver_position_cmd будет присутствовать. Разрешено использовать полный tram_vehicle_msgs из основного датасета: в примере чекера не хватает DriverControllerCommand.msg. |
| Презентация | Не обязательна для текущей загрузки. Нужна на полуфинале/финале при прохождении; отдельно загружать её не требуется. |
| Подача | Все поля формы, до 27 сентября 23:59 МСК. Можно отправлять несколько раз; сохраняется последняя версия. |

## Геометрия и входы

Система base_link расположена в оси вращения передней тележки, на высоте контакта колеса с рельсом. Антенны в этой системе: master=(-9.873,0,3.0) м, rover=(2.563,0,3.0) м. Расстояние между вертикальными осями вращения тележек — 7.55 м.

Входы: `/vehicle/front_bogie_velocity`, `/vehicle/rear_bogie_velocity`, `/vehicle/driver_position_cmd`, позиции `/sensing/gnss/master/fix` и `/sensing/gnss/rover/fix`. GNSS-скорость и эталонный `/localization/kinematic_state` алгоритм не использует. Единицы колёсного потока проверяются отдельно: для предоставленного набора выбран делитель 3.6; подпись единиц в исходном README сохранена как первичный текст.

Выходы: `/result/velocity` типа `tram_vehicle_msgs/msg/VelocitySensor`, м/с; `/result/position` типа `nav_msgs/msg/Odometry`, XYZ base_link в системе карты. Стек ROS 2 Humble, сборка `colcon build`.

## Оценивание

| Технический критерий | Максимум |
|---|---:|
| Точность скорости | 30 |
| Точность положения | 35 |
| Устойчивость, проскальзывание и аномалии | 20 |
| Реальное время и производительность | 15 |
| Итого | 100 |

Отдельный питч на последующих этапах: качество выступления 10, глубина темы 12, ответы на вопросы 8 — всего ещё 30. Эти баллы не являются результатом автоматического теста.

Требования быстродействия: минимум 10 Гц, предпочтительно 20–50 Гц; задержка до 100 мс, пиковая до 250 мс; не более двух ядер и 0.5 ГБ памяти. Точные формулы перевода ошибок в конкурсные баллы не опубликованы в полученных материалах.
