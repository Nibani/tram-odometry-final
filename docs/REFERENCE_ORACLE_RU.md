# Исправление офлайн-эталона в 0.3.1

Патч исправляет сопоставление GNSS fix при повторных и обратных метках времени.
Алгоритм ROS-узла, веса, параметры и обе карты совпадают с версией 0.3.0.
Изменение RMSE ниже относится к составу эталона, а не к улучшению одометрии.

Раньше `paired_reference` передавал в двоичный поиск необязательно отсортированные
метки. Среди 97 уникальных заездов нарушение обнаружено в трёх TRAIN и одном
открытом audit. Во всех 22 validation-заездах порядок корректен.

Новое правило `fix-monotonic-record-high-v1` сохраняет первую запись и далее
только метки, строго превышающие все предыдущие в порядке записи. Координаты
отбираются той же маской. Это совпадает с уже применяемым правилом скоростного
эталона. Повторные/поздние сообщения не сортируются обратно в поток; их отбрасывание
не означает, что каждое такое измерение физически неверно.

Ближайшее сопоставление по-прежнему допускает отклонение до 50 мс включительно;
при равных расстояниях выбирается более поздняя метка. Quality дополнительно
требует `11.9 < длина антенной базы < 12.9` м. Эти пороги и исключение первых
трёх секунд не менялись. Если один из приёмников отсутствует, парного эталона нет.

| Показатель | Oracle до патча | Oracle 3.6 |
|---|---:|---:|
| Validation XYZ raw RMSE, м | 7.863374165 | 7.863374165 |
| Validation XYZ quality RMSE, м | 7.662694748 | 7.662694748 |
| Audit raw число пар | 105389 | 105406 |
| Audit XYZ raw RMSE, м | 31.296397508 | 31.293895482 |
| Audit XYZ quality RMSE, м | 31.943841351 | 31.943841351 |

Меняется только raw-состав заезда `30618_27e994fc`: 36964 → 36981 пар.
Все quality- и скоростные метрики, начальная привязка и выходные траектории
сохранены. Для сравнения с E-02 его неизменные audit-выходы также пересчитаны
новым эталоном: raw RMSE 30.449823164 м, на тех же 105406 парах.

Карта воспроизведена заново из TRAIN. У `30618_40ffd323` промежуточная выборка
движущихся точек меняется 162 → 160, центральных — 110 → 109. Его три локальные
точки подгонки и остальные эффективные входы совпадают точно. Полный набор
остаётся 144 точки из 36 заездов; итоговый CSV побайтово совпадает с 0.3.0.
Старое и новое происхождение сохранено в `results/hairpin_builder_reproduction*.json`
и `results/reference_order_v36/`. Источники двух терминальных дополнений не затронуты.

Проверки без ROS и без обучения:

```bash
python3 tests/test_reference_order.py
python3 scripts/rescore_saved.py \
  --source /tmp/tram-evaluation/evaluation_holdout \
  --cache /tmp/tram-evaluation/cache \
  --out /tmp/audit-with-corrected-reference.json
```

`--source` содержит исходный `metrics.json` и сохранённые `<bag>.npz` с `q/output`.
Пересчитываются только позиционные поля; speed/runtime статистика переносится
из исходного отчёта. JSON явно хранит обе цепочки происхождения, версии и хеши.
Скрипт не заменяет исходный файл и отказывается перезаписывать существующий выход.
Полное воспроизведение через `scripts/reproduce.py` использует новый эталон сразу.

Восемь регрессионных проверок покрывают обратные и повторные метки, независимые
потоки двух приёмников, связь метки с координатами, пустые каналы, границу 50 мс
и отсутствие изменения входов. Старая реализация не проходит четыре содержательные
проверки — это подтверждает, что тесты обнаруживают найденную ошибку.

Показатели ROS/DDS по-прежнему относятся к проверенному запуску версии 0.3.0
[CI 36239255867](https://github.com/Nibani/tram-reserve-odometry/actions/runs/36239255867).
Патч не заявляет нового замера производительности: исполняемая логика и её входные
карты/веса прежние, версия пакета изменена на 0.3.1. Старый архив 0.3.0 и его
приёмка сохранены отдельно. Эта коррекция не доказывает перенос точности на
новые данные или конкурсное место.
